## Prachi's prepared source explanation

**Purpose and input:** A student clicks `#googleLogin` on the landing form. `setupAuthControls` attaches that click to `handleGoogleLogin` in [frontend/apps.js](../../frontend/apps.js). The Remember me checkbox is another input: `applyLoginPersistence` chooses local or session persistence.

**Flow and output:** The handler ignores a click while the form is busy, clears the old error and disables the form. It awaits persistence, creates `GoogleAuthProvider` with an account-selection prompt, then calls `signInWithPopup`. Only a returned credential reaches `startSession(credential.user)`, closes the auth UI and shows the welcome message. A rejected popup goes through `showAuthError`; `finally` clears the busy state so the user can retry. That source branch explains why cancellation can recover without producing a signed-in user; it is not evidence that the success branch ran.

**Dependency and handoff:** [App.jsx](../../frontend/react-app/src/App.jsx) imports Firebase Auth functions and exposes them through `window.campusFirebaseAuth` before the legacy scripts run. [firebase.js](../../frontend/react-app/src/firebase.js) initializes Auth. The real provider flow also depends on the deployed hostname being authorized in Firebase, Google provider configuration, network access and browser popup/persistence behavior. The production domain list is remote configuration; the [redacted repair receipt](../../frontend/react-app/verification/google-signin-domain/results.json) records the specific previous repair. This slice calls Firebase Auth, not the Assistant/photo backend APIs.

**Specific question for a teammate:** “Where does dismissing the Google popup re-enable the form, and why must `startSession` remain uncalled in that case? Trace the SDK bridge and locate the signed-out assertion.” Proposed reviewer: `ujjalpoudel75`; acceptance, answer and actual independent result are **PENDING** in #139.
